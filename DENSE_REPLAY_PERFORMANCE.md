# Dense rooted-session replay

A physical 12,500-read capture (169,574 events, 12,444 block completions) exposed replay taking more than 120 seconds before the native UI could display data. Ingestion alone took about 0.5 seconds. Whole-source FilePath coverage constructed a transaction for every completion.

Repeated request pointers and multiple bio origins expanded the same file identity index repeatedly. The transaction builder also cloned the full same-inode FileIo history for each request. Deduplicating identity keys before expansion and borrowing FileIo records removes these costs. The final candidate positions, ordering, path backfill, confidence rules, and public build_transaction_graph API are preserved.

Regression: set DENSE_REPLAY_NDJSON to the immutable capture and DENSE_REPLAY_REFERENCE to the 200 JSON graphs generated by the pre-change implementation. Run cargo test --release -p android-ebpf-protocol --test dense_replay -- --ignored --nocapture --test-threads=1. The first test compares all serialized graph data and enforces a 2-second graph construction budget; the second enforces a 30-second coverage budget and asserts the raw observed completion/unmatched counts. These are opt-in physical-data performance tests, not portable CI timing assertions. The original code fails the first budget (9.35 seconds). The corrected code produced identical graphs in 0.175 seconds and coverage in 12.16 seconds on the validation host.

This optimization does not repair physical event loss: the capture has 56 missing completion records, 56 unpaired observed completions, and 112 issues without a safe paired completion. Coverage reports Exact 0, Probable 12,386, Unresolved 58 (56 unmatched, one no-origin, one missing-path). Raw input is unchanged. Full native graph interaction acceptance remains a separate gate.
